# Deep Research Agent

一个**从零手写**（不依赖 LangChain / LangGraph 等框架）的深度研究 Agent：给定一个问题，它会自动规划子问题、搜索网页、阅读并提炼内容，最后生成带引用的研究报告。



## 功能

- **自适应规划**：先判断问题复杂度，简单问题只生成 1 个子问题，复杂问题拆成 2-3 个
- **工具调用**：`web_search`（DuckDuckGo 搜索）、`read_page`（抓取网页正文并按关注点提炼要点）
- **上下文管理**：网页原文不直接放进对话，先提炼成 ≤300 字的要点，控制 token 增长
- **来源管理**：由代码记录读过的网页，参考列表由代码生成，避免模型编造链接
- **预算与停止条件**：代码层面限制搜索次数和阅读页数；达到最大步数时去掉工具，强制根据已有信息生成报告
- **可观测性与评测**：记录每一步的 token 消耗；评测脚本对比不同版本的步数、token 和报告质量

## 架构

```
用户问题
   │
   ▼
┌──────────────┐
│  自适应规划   │  判断复杂度 → 1~3 个子问题（JSON 输出）
└──────┬───────┘
       ▼
┌────────────────────────────────────┐
│  Agent loop（最多 10 步）            │
│                                    │
│  LLM 决策 ──► 调用工具？              │
│     ▲            │ 是               │
│     │            ▼                 │
│     │   web_search（≤6 次）          │
│     │   read_page（≤5 页，先提炼要点） │
│     │            │                 │
│     └─── 结果写回 messages ◄─────────┘
│                  │ 否 / 达到上限      │
└──────────────────┼─────────────────┘
                   ▼
        最终报告 + 代码生成的参考来源
```

## 快速开始

```bash
git clone https://github.com/<你的用户名>/deep-research-agent.git
cd deep-research-agent
pip install -r requirements.txt
```

在项目根目录新建 `.env`：

```
DEEPSEEK_API_KEY=你的key
```

运行：

```bash
python agent.py   # 交互式研究
python eval.py    # 运行评测
```

## 设计决策与取舍

| 问题 | 方案 | 取舍 |
|---|---|---|
| 网页内容太长，每一步都要重发全部历史，token 快速增长 | `read_page` 内先用 LLM 按关注点提炼成 ≤300 字要点 | 每读一页多一次 LLM 调用；可能丢失细节 |
| 模型会引用没读过的来源 | 代码维护已读 URL 列表，模型只标 `[编号]`，参考列表由代码生成 | 搜索摘要不能作为引用依据 |
| 想到哪查到哪，步数多、偏题 | 自适应规划：简单问题不拆分，复杂问题拆成 2-3 个子问题 | 规划多一次调用；拆得太少时信息可能不够全面 |
| 模型不遵守提示词里的数量限制 | 搜索次数、阅读页数的上限写在工具函数里，超出时返回提示 | 上限过小可能导致信息不足 |
| 达到最大步数后，前面的研究白费 | 到上限时去掉 tools，强制根据已有信息写报告 | 报告可能不完整 |

## 评测（Eval）

测试集：5 个问题（事实型、概念型、对比型），每个版本运行 2 次取平均。报告质量由 LLM 打分（1-10 分）。

| 版本 | 平均步数 | 平均输入 tokens | 平均阅读页数 | 平均分 |
|---|---|---|---|---|
| 基线（无规划、无上限） | 7.8 | 24,781 | 5.8 | – |
| 规划 v1（每个子问题单独设预算） | 8.8 | 36,089 | 7.2 | – |
| 无规划 + 搜索 / 阅读上限 | 6.5 | 21,605 | 5.0 | 9.2 |
| **自适应规划 + 搜索 / 阅读上限（最终版）** | **5.6** | **16,127** | **3.4** | **8.8** |

**最终版相比基线：平均步数减少 28%，输入 token 减少 35%。**

### 主要发现

1. **规划 v1 反而让成本上升了 46%。** 提示词要求“每个子问题最多搜索 2 次、阅读 2 页”，模型把上限当成了目标；简单问题也被强行拆分（如 LoRA 问题的 token 从 6k 涨到 22k）。改为自适应规划 + 总预算后才真正降低成本。
2. **重要约束要靠代码保证，不能只靠提示词。** 只在提示词里写“最多阅读 5 页”效果不稳定；把上限写进工具函数后，步数明显下降。
3. **搜索次数不设限时会出现反复搜索。** 某次运行中，一个问题用满 10 步、消耗 88k tokens，却只读了 3 页。加入搜索上限后，该异常消失。
4. **LLM-as-judge 在时效性问题上有偏差。** 评审模型的知识有截止日期，会把正确的最新信息误判为编造（“DeepSeek 最新模型”一题，报告内容准确且引用完整，却只得了 3 分）。在评审提示词中要求“不依据自身知识判断事实”后，分数恢复为 10 分。
5. **成本与质量的取舍。** 自适应规划比无规划少用 25% 的 token，但平均分略低（8.8 vs 9.2）：部分问题拆得太少，信息不够全面。

### 局限

- 测试集只有 5 个问题，每个版本只运行 2 次；单次运行波动较大（同一问题 token 消耗可相差 4 倍）
- LLM 评审偏宽松，分数集中在 8-10 分，区分度有限
- 统计的 token 只包含主循环，不包含规划和网页提炼的调用
